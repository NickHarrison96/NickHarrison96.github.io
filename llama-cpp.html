llama.cpp: run models on your own machine

llama.cpp is an open-source C/C++ engine for running large language models locally, in the GGUF format, on CPU and GPU. This guide covers the official installer, the CLI, the server and web UI, and building from source.

Most recent guide. Commands were checked against the official llama.cpp README, llama.app docs, and the current build and server documentation.

1 Installation

The official README gives two command styles.[1] The llama.app installer puts a llama command on your PATH, and you then run llama cli and llama serve. A build from source still produces the llama-cli and llama-server binaries (on Windows, llama-cli.exe and llama-server.exe) in build/bin/.

One-line install

On macOS and Linux:

curl -LsSf https://llama.app/install.sh | sh

On Windows, in PowerShell:

irm https://llama.app/install.ps1 | iex

Then open a new terminal and check the install:

llama --version

Llama app

On Mac and Windows 11 you can also install the Llama app from llama.app. It lives in the menu bar on Mac and in the system tray on Windows, and it sets up the same llama command line for you.

Other official options, all described on the project page, are Docker images, pre-built binaries from the releases page, package managers including Winget, and building from source (section 3).

2 Quickstart

Download a GGUF model from Hugging Face and chat in the terminal. The official README uses this example:[1]

llama cli -hf ggml-org/Qwen3.5-0.8B-GGUF

The llama.app quickstart also shows a Gemma example[4], and you can pin a quant after the repo name with a colon:

llama cli -hf unsloth/gemma-4-E4B-it-GGUF:Q4_0

If you already have a .gguf file on disk, point at it with -m:

llama cli -m my-model.gguf

List models already in the cache with llama cli -cl. To serve a model over HTTP and open the built-in web UI:

llama serve -hf ggml-org/Qwen3.5-0.8B-GGUF

By default the server listens on http://127.0.0.1:9931. Open that address in a browser for the web UI, or call the OpenAI-compatible API (examples in section 7).

3 Build from source

Clone the official repository and use CMake. The default build is CPU-only; turn on one or more GPU backends to match your hardware.[2] The official clone URL is https://github.com/ggml-org/llama.cpp.[1]

git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp
cmake -B build
cmake --build build --config Release

Add -j and a job count to the build step if you want a parallel compile, for example cmake --build build --config Release -j 8. Binaries land in build/bin/.

CMake backend flags

CMake flags for llama.cpp GPU and CPU backends
HardwareCMake flagNotes
NVIDIA GPU-DGGML_CUDA=ONRequires the CUDA Toolkit.
Apple silicon-DGGML_METAL=ONMetal is typically on by default on macOS. Disable it with -DGGML_METAL=OFF.
AMD GPU (HIP / ROCm)-DGGML_HIP=ONOfficial ROCm path. You may also need HIPCXX, HIP_PATH, and a -DGPU_TARGETS= value for your GPU.
Vulkan (cross-vendor)-DGGML_VULKAN=ONDocumented for Windows and Linux, including AMD on Windows.
Intel GPU (SYCL)-DGGML_SYCL=ONOfficial SYCL backend for Intel GPUs. The documented configure also sets -DCMAKE_C_COMPILER=icx -DCMAKE_CXX_COMPILER=icpx.[12]
CPU onlydefault (no extra flag)Works everywhere; slower than a GPU build when a GPU is available.

Example GPU configures, from the official build guide:

# NVIDIA (CUDA)
cmake -B build -DGGML_CUDA=ON
cmake --build build --config Release
 
# Apple silicon (Metal), if you want to set it explicitly
cmake -B build -DGGML_METAL=ON
cmake --build build --config Release
 
# AMD GPU on Linux (HIP / ROCm) — also set HIPCXX, HIP_PATH, and GPU_TARGETS for your card
cmake -S . -B build -DGGML_HIP=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
 
# Vulkan
cmake -B build -DGGML_VULKAN=ON
cmake --build build --config Release

You can enable more than one backend in a single build, for example -DGGML_CUDA=ON -DGGML_VULKAN=ON, and then pick a device at runtime with --device (section 9).

Older notes sometimes used -DGGML_HIPBLAS=ON. The current official flag is -DGGML_HIP=ON.

4 Using the CLI

llama cli (or llama-cli from a source build) is the terminal front end: an interactive chat and a playground for sampling, grammars, and prompts. From a source build, run the binary in build/bin/, or .\llama-cli.exe on Windows.

Set a system prompt, or ask one question and exit when the answer finishes:

llama cli -m model.gguf -sys "You are a concise assistant that answers in bullet points."
llama cli -m model.gguf -st -p "Give me a baklava recipe"

Useful context and offload flags, which also work with llama serve:

llama cli -m model.gguf -c 0 -ngl all

-c 0 uses the context size the model was trained with (this is also the current default). -ngl all offloads every possible layer to the GPU; -ngl auto is the default, and you can also pass an exact layer count.

5 Sampling

These flags shape how tokens are chosen. Defaults below are from the current llama.cpp source (common/common.h).

llama.cpp sampling flags and their defaults
FlagDefaultWhat it does
--temp N0.80Randomness. Lower is more deterministic; higher is more varied.
--top-k N40Sample from the K most likely tokens. Values of 0 or less use the full vocabulary.
--top-p N0.95Nucleus sampling. 1.0 disables it.
--min-p N0.05Drop tokens below this fraction of the top token’s probability. 0.0 disables it.
-n, --predict N-1Maximum new tokens. -1 means no limit.
--repeat-penalty N1.0Penalise repeated tokens. 1.0 is off; values above 1.0 discourage looping.
--repeat-last-n N64How many recent tokens the repetition penalty looks at.
--presence-penalty N0.0A fixed penalty for any token already seen.
--frequency-penalty N0.0A penalty scaled by how often a token has appeared.
--typical N1.0Locally typical sampling. 1.0 disables it.
--dynatemp-range N0.0Dynamic temperature range. 0.0 disables it.
--mirostat N0Mirostat sampler: 0 off, 1 or 2 to enable.

For models that emit a reasoning or thinking trace, official flags include -rea / --reasoning on|off|auto (default auto), --reasoning-budget N, and --reasoning-preserve / --no-reasoning-preserve. Check the model card for the template the model expects.

6 Performance

These flags control memory use and throughput. -ngl is usually the first one to get right on a GPU machine.

llama.cpp memory and performance flags
FlagWhat it does
-ngl, --n-gpu-layersLayers kept in VRAM. Accepts a number, auto (the default), or all.
-t, --threadsCPU threads used for generation.
-tb, --threads-batchA separate thread count for prompt (batch) processing.
-c, --ctx-sizeContext window in tokens. Directly affects memory. 0 (the default) uses the model’s trained context.
-b, --batch-sizeLogical batch size for prompt ingestion (default 2048).
-ub, --ubatch-sizePhysical batch size (default 512).
-fa, --flash-attnFlash Attention: on, off, or auto (the default).
--mlockLock the model in RAM so it is less likely to be swapped to disk.
-cmoe, --cpu-moeKeep Mixture-of-Experts expert weights on the CPU. Related: -ncmoe / --n-cpu-moe.
--prio NProcess priority.
--poll NPolling level, from 0 to 100.
--cpu-mask, --cpu-rangePin the process to specific CPU cores.

If generation is very slow, try a lower -t first (even -t 1) to see whether the CPU is oversaturated, then set -t to the number of physical cores. If you run out of memory, reduce -c, then --batch-size, then -ngl, or use a smaller quant (for example Q4_K_M instead of Q8_0).

7 Server, API and Web UI

llama serve (or llama-server from a source build) starts an HTTP server with an OpenAI-compatible API, an Anthropic-compatible /v1/messages endpoint, and a built-in web UI. The current default bind address is 127.0.0.1:9931.[7]

llama serve -hf ggml-org/gemma-4-e4b-it-GGUF:Q4_0
llama serve -m my-model.gguf -c 16384 -ngl all --port 9931

A minimal chat-completions request, from the official docs:

curl http://localhost:9931/v1/chat/completions \
-H "Content-Type: application/json" \
-d '{"messages": [{"role": "user", "content": "Hello!"}]}'

Or from Python with the OpenAI SDK, pointing base_url at http://localhost:9931/v1.

Useful server flags, from the official serve docs and server README:

  • --host and --port — default 127.0.0.1:9931. --host 0.0.0.0 listens on every interface, so only use it when you intend other devices on the network to reach the server.
  • --api-key KEY — require an API key (comma-separated for more than one key).
  • --no-webui — serve the API only.
  • -np, --parallel N — number of server slots for concurrent requests.
  • -a, --alias NAME — model name reported by the API.

The API includes OpenAI-compatible routes such as /v1/chat/completions, /v1/completions, /v1/embeddings, /v1/rerank and /v1/models, plus native llama.cpp endpoints. Streaming, JSON-schema structured output, and tool calling are documented in the official API and server pages.[8][6]

Web UI

Open http://localhost:9931 after starting the server. Official docs describe multimodal attachments, Markdown rendering, conversation branching, and a settings panel.[9] If 9931 is already in use, pass another port with --port.

Router mode

Launch llama serve with no model to start a router that can load and unload models on demand[7]:

llama serve

Models can come from the Hugging Face cache (llama serve -cl lists it), a models directory (--models-dir), or a preset file (--models-preset). Requests need to name the model.

8 Advanced features

Multimodal input

llama.cpp handles image, audio and video input through libmtmd.[11] The dedicated binary from a source build is llama-mtmd-cli. llama-server / llama serve can also load a multimodal projector.

# Hugging Face model that includes a multimodal projector
llama-mtmd-cli -hf ggml-org/gemma-3-4b-it-GGUF
 
# Local text model plus a separate projector
llama-server -m gemma-3-4b-it-Q4_K_M.gguf --mmproj mmproj-gemma-3-4b-it-Q4_K_M.gguf
 
# Load the model without offloading the projector, or with multimodal disabled
llama-server -hf ggml-org/gemma-3-4b-it-GGUF --no-mmproj-offload
llama-server -hf ggml-org/gemma-3-4b-it-GGUF --no-mmproj

Vision and OCR models are often trained with a particular prompt layout and may need a larger context, for example -c 8192. Check the model card.

In the interactive CLI, official llama.app docs also describe /image and /audio slash commands[5], and --image / --audio flags.

LoRA adapters

# One or more adapters (comma-separated)
llama-cli -m base.gguf --lora adapter.gguf
llama-cli -m base.gguf --lora a.gguf,b.gguf
 
# Custom scales, current format: FNAME:SCALE
llama-cli -m base.gguf --lora-scaled adapter.gguf:0.5
llama-cli -m base.gguf --lora-scaled a.gguf:1.0,b.gguf:0.8

The current flag is --lora-scaled FNAME:SCALE (comma-separated for more than one). Older notes that used a space, such as --lora-scaled adapter.gguf 0.5, no longer match the official parser.

GBNF grammars

You can constrain the output to a formal grammar, such as JSON:

llama-cli -m model.gguf --grammar-file grammars/json.gbnf -p "Generate a user profile:"
llama-cli -m model.gguf --grammar 'root ::= "yes" | "no"' -p "Is the sky blue?"

Chat templates

llama-cli -m model.gguf --chat-template phi3

You can also pass a custom template string with --chat-template. Reasoning-capable models may need --reasoning-preserve or --no-reasoning-preserve, as noted in section 5.

Speculative decoding

A draft model can be passed for speculative decoding. Official flags include -md / a draft model path and --spec-type. See llama-cli --help or the CLI docs for the types your build supports.

9 Runtime devices

Once the binary includes the backends you need, choose a device at launch:

llama-cli --list-devices
llama-cli -m model.gguf --device CUDA0 --n-gpu-layers all
llama-cli -m model.gguf --device Vulkan0 -ngl all
llama-cli -m model.gguf -ngl 0

--list-devices prints the backends the binary can see[2] (for example CUDA0 or Vulkan0). -ngl 0 keeps the model on the CPU. On Windows, quote paths that contain spaces: llama-cli.exe -m "C:\My Models\llama.gguf".

10 Troubleshooting

Is the GPU actually being used?

Watch the startup log for a line like offloading N repeating layers to GPU and a report of VRAM used. If you do not see layers being offloaded, the model is running on the CPU. Confirm you built with the right backend, that --list-devices shows the GPU, and that -ngl is not 0.

Older guides quoted a [cublas] offloading … layers line. Current llama.cpp logs the offload without that [cublas] prefix.

The GPU is missing from --list-devices

The backend was probably not compiled in, or the driver is not visible. Rebuild with the correct -DGGML_* flag and update GPU drivers. If the device is listed but inference still runs on the CPU, pass --device … and -ngl all, then re-check the load log.

Out of memory

Reduce the largest consumers in this order: context (-c), batch size, GPU layers, then the quantisation level.

Port 9931 is already in use

Pass another port with --port, for example --port 8081.

11 Practical workflow

  1. Install with the official one-line script or app, or build from source with the right backend (section 1 or 3).
  2. Confirm the install with llama --version. For a source build, run llama-cli --list-devices and check the GPU is visible.
  3. Start simple: llama cli -m model.gguf or llama cli -hf repo:quant.
  4. Tune sampling. Raise --temp / --top-p for more variety; lower them for tighter answers; add a repeat penalty such as --repeat-penalty 1.1 if the model loops.
  5. Fit the machine: try -ngl all, then lower it until VRAM is enough. Keep -c only as large as you need. Raise --batch-size if prompt ingestion is the bottleneck.
  6. When you need an API or a browser UI, switch to llama serve on http://127.0.0.1:9931.
  7. Add LoRA, grammars, multimodal, or a chat template only once the basic run is stable.
